Home library: capture and review app

2026-10-13 · implementation plan for Miro · planning council: Opus 5.5, Fable 5.1, GPT-6.1 Sol, GPT-6 Astra · synthesis by Opus 5.5

Summary Key decisions Phases Risks Open questions

Summary

No native app. We build one small Python web app next to the existing hl pipeline:

  • Stack: FastAPI with server-rendered pages (Jinja and HTMX) and a little JavaScript for the capture page.
  • Data: one SQLite file for the catalog and the job queue.
  • Reading: one worker process runs hl on each new photo.
  • Hosting: it runs in WSL on battlebox. Every device reaches it privately over Tailscale with HTTPS.
  • Devices: on the Android phones it is installed to the home screen and used for photos. On the iPad and the laptop it is just a website, used for review with the keyboard.
  • No Apple account, no Mac, no MacinCloud.

Before any real code, a few evenings of phase 0 tests check the facts the plan rests on. Do the phones upload full-resolution photos from the browser? Does battlebox stay reachable? Do cover and barcode photos work? Is Grist good enough to make our own review page unnecessary?

Then come three build phases: the back end, the web pages, and day-to-day operation. An Expo Android app stays in reserve for one case only: if taking photos in the browser fails.

All four council seats agreed on this overall shape. The real disagreements were about the data model, how photos are named, and how the worker calls the pipeline. Each is settled below, with its reason.

D2 Hosted at home on battlebox, in WSL2. Reached through Tailscale Serve, which gives the HTTPS a PWA needs. The app itself listens only on localhost.
Fable, Sol, Astra; Opus flagged the laptop sleeping		 A cloud web app with a worker at home. It would be a second deployment with its own login and a sync path between the two. The reading must stay at home anyway, because Codex and Pi run on your subscriptions. Battlebook, the laptop, loses because it sleeps and leaves the house.
D3 The app's own SQLite file is the store, unless Grist wins a one-evening test in phase 0. There is only ever one catalog that people edit.
Gate from Sol and Astra · one-evening time-box from Fable · Opus and Fable favoured SQLite		 Grist as both store and review screen. R7 allows it, and the spec planned this test. It probably loses because review needs things specific to the pipeline: the tile the book was seen in, the second reading, and the catalogue candidates. Grist cannot show those. We still test it, cheaply, with 20 existing rows.
D4 Three separate things: captures, observations and books.
  • A capture is a photo that was uploaded.
  • An observation is one row of records.json. It is evidence, not a book.
  • A book is one physical copy. It exists only once a person approves it, with a state and a location.
Sol, Astra		 Importing every pipeline row as a book (Opus, Fable). That breaks the counts: unparsed, incomplete and unreadable rows are not books, and a shelf photo plus a cover photo describe the same book twice.
D5 Each capture gets an ID from the phone. The phone makes up a unique ID (a UUID) for each upload. It is the upload's idempotency key, so a retried upload is recognised and not stored twice. It is also the photo's name in the pipeline's work directory. The SHA-256 of the file is stored too, but only to warn about duplicates.
Sol, Astra		 Naming each photo by its content hash (Opus, Fable). The same bytes can be sent twice on purpose, for example to fix a wrong location, and the hash would treat that as the same capture. The UUID needs no change to the pipeline either: workspace.photo_dir keys on the file stem.
D6 One worker runs hl as a separate process, in its own process group.
  • It takes jobs from a SQLite job table.
  • It reports a heartbeat while it works. A job counts as stuck after 20 minutes.
  • A results write from an attempt that has since been superseded is refused.
Subprocess from Sol and Astra · timeout from Fable · queue from the research note		 Calling the pipeline functions directly from Python (Opus, Fable). That is simpler, but a hung codex or pi call could not be killed cleanly, and a crash would take the worker down. The hl command is the documented, stable contract. Celery and Redis lose too: they are too much machinery for one worker.
D7 Cover and barcode photos go into phase 1.
  • A new hl cover command does two blind reads of a single image.
  • Barcodes are decoded on the server with zxing-cpp. The ISBN is checked and passed to the ISBN look-up path, which is already built.
All 4 seats		 Scanning barcodes live in the browser. Its behaviour on your phones is untested. Shelf photos alone are not enough either: many thin books have no spine text (spec 2.4).
D8 Photos are uploaded while the page is open, with retries. The phone keeps no queue of its own in version 1. The capture page offers two ways in: pick several photos from the gallery, or take one with the camera. Photos taken with the normal camera app stay in the camera roll, so nothing is lost if an upload fails. Phase 0 decides which of the two ways is the main one.
Fable, Sol; Opus and Astra wanted the queue now		 A queue stored on the phone (IndexedDB) from day one. How reliable it is has not been checked. Capture mostly happens on home Wi-Fi, and the camera roll already serves as the backup. The queue becomes a later slice if uploads get lost in practice.
D9 Login comes from Tailscale. Tailscale Serve passes on who is connecting (its Tailscale-User-Login header). The app allows exactly two logins, protects edits against cross-site requests, and gives harness agents a separate token.
Sol, Astra		 Just a name cookie (Fable): it records nobody reliably. A public site with its own login: more code, and it is exposed to the internet. The bookshop check works over Tailscale anyway.
D10 Agents use the JSON API, or hl catalog … commands that go through the same checks. This meets R3.
Astra, Opus		 Agents writing to SQLite directly. That skips the checks, for example that an approved book has a state and a location.

Phases

Every build step follows your red, green, review and refactor loop with small commits. Each phase ends with a check on the real devices. The work goes on a new branch taken from t3code/implement-home-library. Photos, the database and work files live under ~/home-library/ on battlebox, never in the repository. The existing refuse_inside_checkout guard and tests/test_repo_privacy.py extend to them.

Phase 0: tests that de-risk the plan, no production code S–M · 2–3 evenings
  1. Host check. On battlebox's WSL:
    • Install Tailscale and turn on systemd.
    • Check that codex exec, pi and yaz-client run headless.
    • Reboot Windows without logging in, and check that WSL and a test service come back.
    Kill criterion: if battlebox can't run unattended, pick another host (question 1).
  2. Capture test. A throwaway FastAPI page of about 40 lines, served with tailscale serve.
    • On both phones, upload the same shelf twice: once through <input type=file accept=image/* capture=environment>, and once through a gallery pick with multiple.
    • Compare size (should be 4080×3072), EXIF orientation, format (JPEG or HEIC) and sharpness against the original in the camera roll.
    • Install it as a PWA on both phones, and open it on the iPad.
    Kill criterion: if the photos arrive smaller than the original, phase 4 (Expo) moves ahead of phase 2's capture page.
  3. Cover and barcode test. Take 10 cover photos and 10 barcode photos, in all three languages.
    • Read the covers with the existing hl read on one image.
    • Decode the barcodes with zxing-cpp, then call find_candidates(isbn=…).
    This settles whether covers need two reads, and the cover prompt.
  4. Store test, one evening only. Put 20 rows from an existing records.csv into Grist and into Sheets, and correct them on the iPad with the keyboard. If Grist feels good, decide D3 for Grist: phase 2 then shrinks to the capture and status pages, and the worker writes to Grist.
  5. Answer key. You confirm the provisional answer key for the four test shelves (spec §3.2), so later accuracy numbers mean something.

Output: docs/research/app-spikes.md, with what was measured and a go or no-go for each kill criterion.

Phase 1: back end with uploads, worker and catalog L

1.1 Layout

  • New modules: home_library/store.py (SQLite, numbered SQL migrations), home_library/worker.py and home_library/web/ (FastAPI app, templates, static files).
  • New dependencies: fastapi, uvicorn, jinja2, python-multipart, zxing-cpp. Add pillow-heif only if phase 0 shows HEIC files.
  • Data root: ~/home-library/, holding catalog.db, captures/ and work/.

1.2 Schema

TableHolds
locationsname ("Box 3", "Shelf A2"), kind (shelf or box)
capturesthe UUID from the phone, kind (shelf, cover or barcode), location, default state, who uploaded it, original name, sha256, size, time, and group_id, which pairs a cover with its barcode
jobscapture, status, attempt, owner token, heartbeat, last error, started and finished times
observationsone row of records.json: capture, attempt, row index, read_status, title, other_reading, the remaining columns as JSON, a link to its candidates, status (open, used or dismissed), and the book it became
booksthe fields of spec 2.1, plus state, location, cover capture, needs_review, a version number for edit conflicts, and who created and who reviewed it

A full-text index (SQLite FTS5 with the trigram tokenizer) over title, sort key, author and series. Trigrams handle kana and kanji, and Czech text with diacritics, without a word splitter.

1.3 Upload

  • POST /api/captures sends the file, the capture UUID, kind, location, default state and an optional group.
  • The server writes the file to a temporary file, flushes it to disk and moves it into place. It then records the capture and its job in one transaction and returns 201 with a receipt.
  • The same UUID sent again returns the same receipt and adds nothing.
  • Type and size are checked. The original file name is never used as a path.

1.4 Worker (hl worker)

  • It claims a job in a short BEGIN IMMEDIATE transaction and commits before any model work starts.
  • It runs hl run captures/<uuid>.jpg --location … --work-root … as a separate process with a timeout, and reports a heartbeat every 30 s.
  • When the run ends, it imports records.json as observations and marks the job done, in one transaction. The import is refused if the job's owner token has changed.
  • It makes at most 3 attempts. A failure shows in the app, including after a restart.
  • Only one job runs at a time, which respects the home uplink rule in docs/pipeline.md.
  • A rerun adds new observations and never overwrites a book a person has edited.

1.5 Covers and barcodes

  • hl cover: one image, scaled to at most 2000 px on its longest side, and a new prompts/cover_read.txt. It runs the same two blind reads and merge, then a look-up with author and title, then the pick.
  • hl barcode: decode with zxing-cpp, validate the ISBN-13 checksum and the 978/979 prefix, and guess the language from the registration group (4 Japanese, 80 Czech, 0 and 1 English; otherwise try all sources). Then use the ISBN path of lookup.find_candidates.
  • A cover and a barcode with the same group_id give one observation. A barcode that cannot be decoded falls back to typing the number in.

1.6 API for agents

JSON endpoints for books, observations, locations and jobs, plus hl catalog list|show|edit|move calling the same functions. A short docs/harness.md tells Claude Code and Codex how to use them (R3).

1.7 Tests

  • The worker gets a fake hl runner, the same way tests/test_reader.py fakes codex. Images are generated, and catalogue answers come from fixtures.
  • Cases to cover:
    • a repeated POST;
    • the same file name with different bytes;
    • a crash after the upload or after the import;
    • a worker that dies;
    • a stale attempt completing late;
    • a broken image and an invalid barcode;
    • an edit that conflicts with another;
    • a rerun that must keep a human's correction.
  • Real check: upload the four test photos with curl. The observations must match what hl run produced on 2026-10-05, and a second upload must add no job.
Phase 2: web pages for capture and review L · S if Grist won
  • Shell. A base template, a PWA manifest and a minimal service worker that exists only so the app can be installed. It does no offline caching. Big touch targets, plus keyboard shortcuts on the larger screens.
  • Capture page (phones).
    • Pick a location and a default state once; they are remembered.
    • Choose a mode: shelf, or one book. One book means a cover photo, then an optional barcode photo, then the next book.
    • The photos to send show as thumbnails, then upload with a progress bar and retries.
    • Each photo shows a clear status: on this phone, received, reading, needs attention or ready for review.
  • Review page (iPad and laptop).
    • An inbox of open observations, grouped by photo and location.
    • Each detail shows:
      • the tile from where, with the full photo a tap away;
      • both readings, and the reason for the review;
      • the catalogue candidates from candidates.json, with "use this record";
      • editable fields.
    • Actions: approve as a new book, merge into an existing book, dismiss, attach a cover, or add a book by hand.
    • Shortcuts: j/k to move, Enter to approve and go to the next, e to edit.
    • Moving or changing the state of several books at once.
  • Catalog. Search by title, author, ISBN or series, and filter by state, location and tag. It works on a phone for the bookshop check.
  • Locations and status. A page to create, rename and list locations. A status page shows the job queue, the worker's heartbeat and the last error, for example "Codex needs a new login".
  • Tests.
    • FastAPI's TestClient on the HTMX fragments.
    • A Playwright smoke test in Chromium and in WebKit, which is close to Safari: capture with a generated image, upload, review with the keyboard and search.
    • Two people editing the same book at the same time.
  • Real check. Both adults photograph one shelf and five covers, and review them on the iPad until nothing is left open. Then search for a book on a phone over mobile data. Time a whole shelf taken cover by cover (spec §3.1).
Phase 3: running it, backups and export M
  • Services. systemd user services in WSL for web and worker. Windows Task Scheduler starts WSL at boot. The PC is set not to sleep. A /health page.
  • Access. Tailscale on both phones, the iPad and the laptop. Tailscale's access rules let only the two family logins in. A token for harness agents that can be revoked.
  • Backups.
    • Every night, a consistent database snapshot with VACUUM INTO, plus captures/ and work/.
    • Copied to Battlebook over Tailscale. A cloud copy only if the family agrees (question 2).
    • A restore onto a clean directory is tested once.
  • Export. /export.csv in UTF-8 with a BOM, using the formula escaping records.py already does, plus a complete JSON export with a list of photos. So a spreadsheet stays a possible end state (R7).
  • Real check. Reboot battlebox and see the app come back with nobody logged in. Reach it over mobile data. A device outside the tailnet is refused. Restore from backup on Battlebook.
Phase 4, only if needed: Expo Android capture app M · conditional

Only if phase 0 or real use shows that capture in the browser keeps failing.

  • EAS Build makes an APK in Expo's cloud. It is installed from a link, with no Play Store account.
  • It talks to the same POST /api/captures.
  • The iPad stays on Safari. No Apple account is needed.
After the build: cataloging the collection

Do one real shelf and one real box end to end (spec §3.5), fix what hurts, then the whole collection. The work is done when every book is in the catalog with a state and a location (spec §1.2), not when the photos have been processed.

Open questions

Answer with a number and "default" or "alt", for example "1 default, 3 alt".

  1. Which machine runs the app and the worker, always on?

    default battlebox, in WSL2. Battlebook holds the backup copy.

    alt A small always-on Linux box at home, for example a mini PC. It is more reliable than WSL, but it's new hardware.

  2. May photos of the home and the catalog leave the house, for a cloud backup or hosted Grist?

    default No. Backups go to the second machine over Tailscale only.

    alt Yes, as an encrypted backup to Google Drive.

  3. Is it fine for your wife's phone and the iPad to run Tailscale?

    default Yes. It is a one-time setup, and it gives the bookshop check from anywhere.

    alt No. Then the app works only on home Wi-Fi, with no access away from home.

  4. Is the one-evening Grist test (phase 0, test 4) still worth doing, given that a custom review page is planned?

    default Yes, time-boxed. If Grist feels good on the iPad, it saves most of phase 2.

    alt Skip it and go straight to the SQLite store and our own review page.

  5. Is a cover photo required for every book?

    default No. A cover photo is required only for books the shelf photo couldn't identify. Others are optional.

    alt Yes, for every book, because it doubles as the catalog picture.

  6. A book that leaves the house, sold or given away: keep it or delete it?

    default Keep it with a fourth state, "Gone", so the bookshop check still answers "we had it".

    alt Delete it.

  7. How are locations named on the physical labels?

    default "Shelf A1", "A2" and so on per bookcase, and "Box 1" to "Box 7". They are created in the app's locations page.

    alt Free names chosen by the family, such as "Hallway top".

  8. Should the second, checking read stay Muse Spark 1.3 through Pi?

    default Yes, as built. A different model catches misreadings that Sol repeats.

    alt A second Sol session (--second-reader codex-exec), with one subscription fewer to keep logged in.

  9. Should the Apple account from your work be used at all?

    default No. This plan needs no Apple account.

    alt If a native iPad app is ever wanted, use a personal $99/yr account.
